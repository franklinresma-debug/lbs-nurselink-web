Bulk nurse import

Prepare migration batches and review the protected import queue in this administration workspace.

Choose an import workflow

CSV, JSON and ZIP: use the private staging importer below to map fields and review rows. Limit: 10 MiB and 2,000 applicant rows per file. SQL dumps can be quarantined there for isolated technical conversion; they are never executed by the application.

Existing Excel / document intake: XLSX rosters and PDF, DOCX, JPG/JPEG and PNG documents use the Temporary Encoder workflow and the existing review queue. Its upload limit is 15 MB per file. Convert XLS to XLSX and DOC to DOCX before using that workflow.

The older document extractor reads at most 120,000 characters, so large Excel files may be truncated. The new CSV/JSON staging reader does not use that extractor: it rejects oversized batches instead of silently dropping rows.

Live legacy migration remains blocked until source mapping, backup/restore, isolated dry-run reconciliation, duplicate and rollback rules, and authorized staff sign-off are approved. Staging is a review step, not migration approval.

Stage CSV, JSON, ZIP or SQL for migration review

Review staging only. This workflow stores source files and validation reports privately. It cannot create applicant accounts, approve memberships, trigger notifications or send rows to the live import queue. Source mapping, isolated dry-run evidence, backup/restore, duplicate and rollback rules, and staff approval are still required.

Limits: 10 MiB per upload; 2,000 applicant rows and 50 source columns per CSV/JSON batch. Oversized or malformed inputs are rejected in full. ZIP packages allow 250 entries and 30 MiB total expanded size. Only your own batches are visible; Super Administrator access is required.

File layouts and preparation
  • CSV: UTF-8 text, one header row, one applicant per record. Choose comma, semicolon or tab delimiter. Quoted commas, quotes and multiline values are supported. Preserve legacy IDs and phone numbers as text.
  • JSON: a flat array of applicant objects, or an object containing an applicants array. Quote identifiers and phone numbers; nested fields need a separate approved mapping. Keep cells under 4,000 characters.
  • ZIP: include manifest.json, one CSV/JSON applicant file and optional PDF, DOCX, JPG/JPEG or PNG documents. Use simple relative filenames. Each document must link to a legacy ID. Documents remain unscanned and quarantined.
  • SQL: accepted into quarantine for technical conversion only. A technical lead must inspect the dump and restore it in a disposable isolated database, then export approved CSV/JSON. The application never executes uploaded SQL.

Example CSV headings: legacy_id,full_name,email,phone,birth_date. Map the actual source headings after upload. Legacy ID, full name and email must be mapped for validation; missing or invalid values are flagged for review. Unmapped source fields are retained in the review, not discarded.

Example JSON:

{"applicants":[{"legacy_id":"L001","full_name":"Sample Applicant","email":"sample@example.invalid","phone":"+639171234567","birth_date":"1990-01-15"}]}

Example ZIP manifest:

{"data_file":"applicants.csv","documents":[{"legacy_id":"L001","path":"documents/L001-cv.pdf"}]}

Use a stable source-system code for every batch from the same dataset. Identical reuploads reuse the same staging batch. Duplicate legacy IDs within the same source and existing-account email matches are flagged; no records are merged. Name/phone matching, historical applications and qualification mapping require further staff decisions.
